# 後半授業の学習順序と教科書設計

更新日: 2026-10-30

後半授業では、ページを表示するところから始め、名前で接続し、データを保存し、教員提供アプリをDBへ接続する。最後に、必要な操作が成功し、不要な操作が拒否されることを確かめる。教科書は、この構築を学生が理由と仕組みから理解するための共通資料とする。

今回の本人指示により、既存のJDU-Web-Infrastructureリポジトリを使用し、OS・Linux教科書の構成・説明方法を参考にして独立した教科書の設計へ進む。2026-10-23の「まずP/Mのみ」は当時の制作範囲である。学習順序と必要知識を整理し、続いて[全14章の章・節・説明内容](textbook-outline.md)を具体化した。本文全章の制作や実装変更は行っていない。

## 完成するシステム

現行演習は、公開サブネットの踏み台・Web、プライベートサブネットのDNS・DB・専用配布repoという5台構成である。学生は教員提供アプリの配置と設定を行う。アプリのプログラミングは課さない。

| 用途 | 通信の流れ |
| --- | --- |
| 一般利用 | 学生PC → HTTP TCP/80 → 公開WebのNginx → 同じWeb内のGunicorn・Django TCP/8000 → 内部DB TCP/5432 |
| 名前解決 | 踏み台・Web → 内部DNS UDP/TCP 53。WebはDB名を解決して接続する |
| 管理 | 学生PC → RDP TCP/3389 → 踏み台 → 各サーバーのSSH TCP/22 |
| アプリ管理 | 踏み台 → Webのprivate IP TCP/8080 → 同じWeb内のアプリ |
| 補助管理 | CloudShell → SSM → 各EC2。一般Web利用の経路とは別である |

GunicornはWeb自身の127.0.0.1:8000で待ち受ける。内部DNSの名前を使ったWeb表示は踏み台から確認する。学生PCの通常DNSでlab.testが解決できることは前提にしない。専用repoは教材・パッケージの配布基盤であり、一般利用者のWebリクエストを中継するサーバーではない。

## 授業の順序と必要知識

以下は学習段階であり、授業回数や教科書の章数ではない。

| 順序 | 学習段階 | 直前に必要な知識と新しく学ぶ内容 | できるようになること | 現行演習 |
| --- | --- | --- | --- | --- |
| 1 | 全体像と実行場所 | クライアントとサーバー、各サーバーの役割。学生PC・CloudShell・踏み台・対象サーバーの違い。Linuxのユーザー・パス・サービスの復習 | 誰がどの端末から何を操作しているか説明する | P0 / M0 |
| 2 | AWSと通信経路 | EC2、VPC、IP/CIDR、公開・非公開サブネット、ルート、IGW、Security Group。RDP・SSH・SSM、利用経路と管理経路の違い | 準備済み構成の通信表を読み、到達条件と制限を説明する | P0から全体に共通 |
| 3 | HTTPと静的Web | URL、HTTP要求・応答、ヘッダー・本文、ステータスコード、Nginx、配信ファイル、待受、アクセスログとエラーログ | まずIP指定でページを返し、応答とログから動作を確認する | P1 / M1 |
| 4 | DNSと名前解決 | ドメイン名、FQDN、ゾーン、権威DNSとリゾルバー、A・NS・SOA、TTL・キャッシュ、転送、UDP/TCP 53、NXDOMAIN、問い合わせACLとゾーン転送制限 | 同じWebを名前で開き、WebからDB名を解決する。指定DNSへの直接問い合わせと通常の名前解決を区別する | P2 / M2 |
| 5 | 保存と停止・再開 | メモリと永続保存の違い、EBSとファイルシステム、パス・所有者・権限。Stop/Start・reboot・削除の違い。再開後のIPとサービスの再確認 | 同じWebと元root volumeでファイル内容と属性の保持を確かめる | P3 / M3 |
| 6 | DBとPostgreSQL | DBが必要な理由、表・行・列・主キー、基本SQLとSELECT。OSユーザー・DB roleの違い、DB所有者、認証と認可、待受、pg_hba.conf、SCRAM | Webから内部DBへ正しいroleで接続し、SQL結果を確認する | P4 / M4 |
| 7 | アプリとDBの統合 | 静的表示と動的表示、Nginxのリバースプロキシ、Gunicorn・Djangoの役割、venvと依存、設定ファイル・秘密情報、migration、初期データ、setup/runtime role、管理画面のログインと操作権限 | 配布済みアプリを動かし、画面の登録・変更がDBと一般画面へ反映されることを確認する | P5。M2の完了が前提 |
| 8 | 最小権限と公開範囲 | OS権限・DB権限・アプリ権限・通信制御の違い。公開80・管理8080・loopback8000の境界。構築用権限の終了、公開・非公開データの分離 | 正規操作が成功し、管理画面・秘密情報・過剰なSQL操作への不要なアクセスが拒否されることを確認する | P6 → M5 → M6 |
| 9 | 観測と障害対応 | DNS、経路、待受、HTTP、アプリ、DB認証・権限の確認方法。期待結果と実結果、変更前後の比較、再確認 | 症状から確認先を選び、原因・修正・復旧結果を説明する | 全段階に共通。新規の採点課題は追加しない |

HTTPをDNSより先に扱うと、IPで動作するWebを基準に、名前解決を加えた結果を比較できる。DB単体の認証接続をアプリより先に確認すると、アプリ接続失敗をDB・DNS・アプリ設定へ切り分けやすい。セキュリティーとログ確認は各段階から扱い、最終段階で全体を照合する。

現行の推奨演習順は、P0 → M0 → P1 → M1 → P2 → M2 → P3 → M3 → P4 → M4 → P5 → P6 → M5 → M6である。P6でpractice側の一時setupを終了してからmission側のアプリ構築へ移る。P/M番号とWEB単元番号は同じではない。

## OSとLinux教科書から引き継ぐ書き方

参照先はOS-Linux-Controlの現行2026年度教材とする。旧JUD project内の控えより現行教材を優先する。

- 章別Markdownを本文の正本とし、理由・仕組みを文章と図で説明する。読書用HTMLとA4縦PDFへ展開できる構成にする。
- 一般的な概念、具体例、出力の読み方、章末問題、解答を揃える。PDFでは章末問題のあと、解答を次ページから始める現行形式を参考にする。
- 教科書、完全手順付き練習P、自力課題M、用語集・コマンド早見表を分け、相互に参照できるようにする。教科書へ採点手順やMの完成コマンド列を埋め込まない。
- 章数・ページ数・一コマの説明時間から本文量を決めない。学習順に必要な知識が説明済みであることを優先する。
- OS・Networkの本文を複製せず、必要な前提を明示して該当教材へ案内する。
- 図は送信元、宛先、実行場所、プロトコル、ポートを明示する。DNSが返すIPと、その後のHTTP・DB通信を別の矢印で示す。
- 製品名の操作だけで完結させず、NginxはWebサーバーとproxy、BINDはDNS、PostgreSQLはDBという役割を先に説明する。

DNSでは現行演習が必要とするA・NS・SOAを中心に説明し、CNAMEは関連する名前の仕組みとして補足できる。DBのSQLは表と基本操作の理解から始め、現行の細かい権限表を理解するためにGRANT/REVOKE、所有権、列権限、sequenceを段階的に説明する。

同日の本人指定により、学生が設定しないCookieやログイン状態の内部機構、CSRFの仕組みは教科書本編の説明対象から外す。学生は管理画面の正規ログイン・許可された操作・ログアウト後の拒否を確認する。DBの補助表は学生が設定するSQL権限の理由まで説明し、アプリ内部の実装解説へ広げない。

## 実装との対応と制作上の境界

P0〜P6/M0〜M6の三言語教材、5台構成、教員アプリ、固定62素点checkerは既存資産として使う。古い単元READMEの4台構成や「アプリ未実装」を現在の状態として再採用しない。追加disk、backup/restore、アプリ開発、本人実演を今回の必須演習へ追加しない。

2026-10-30のポータルREADMEでは、本人用の課題確認と成績原本への自動保存、教師一覧は実AWS受入済みである。新規5台のブラウザ準備、M3停止前後とM5/M6秘密入力のブラウザ導線、一般配布は別残件である。これらは授業運用側の機能であり、学生がWebシステムを構築する学習順序とは分けて管理する。以後の実装状況はポータルREADMEの最新記録を参照する。

教材49手順を新規学生が最初から辿る通し試験、母語校閲、教師の目視確認は、現行の検証記録で未実施である。初期署名版r2の期限は2026-10-27であり、次の授業実施前には配布版・教材helperの照合と再受入が必要となる。教科書の目次整理だけで授業準備完了とはしない。
