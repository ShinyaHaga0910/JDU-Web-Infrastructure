## 選定と目的

教員提供アプリは、Djangoの標準管理画面を使った小さな「JDU備品カタログ」とする。一般入口で公開備品を一覧表示し、管理者入口でログインして架空の備品を登録・編集する。登録した内容をPostgreSQLへ保存し、一般画面を再読み込みすると反映される。

ユーザー指定の必須要件は、一般／管理者入口の分離、DBへの登録、学生がアプリコードを書かないこと。題材・最小機能・必要な設定はCodexが選定するよう委任された。

これは完成済みの市販アプリをそのまま配る案ではなく、Djangoの既存管理機能を使う教員制作アプリ。学生用コード開発課題は設けない。Djangoは認証・管理画面を提供しPostgreSQLへ対応するため、授業の目的に合わせた小さな構成を作れる（一次出典参照）。

## 1. 画面と表示内容

### 一般入口

- 一般利用者はログインなしで、公開状態の備品の一覧を閲覧する。
- URL: 学生PCから`http://<Webの現在の公開IPv4>/`。DNS演習時は踏み台内のbrowserから`http://web.lab.test/`。
- 一覧に備品コード、備品名、数量、架空の保管場所、説明を表示する。
- DBの公開対象を毎回取得し、HTMLの固定一覧やJSONファイルだけで表示を代用しない。
- 一般入口に登録・編集・管理者ログインの操作を置かない。リンクの非表示だけで制限を実現したとは扱わない。

### 管理者入口

- 踏み台上のbrowserから`http://admin.lab.test:8080/admin/`へ接続する。
- 管理者としてログインし、備品の一覧、新規登録、編集、公開／非公開の切替を行う。
- 新規登録と、登録結果の一般画面への反映を必須の完成動作とする。編集と公開切替は利用可能にするが、採点項目の追加はD11で決める。
- 一括削除、一般利用者の会員登録、画像/file upload、貸出・予約、通知メール等は今回の機能に加えない。削除機能は教員側の設定で無効化する。
- 学生が利用するアプリ管理者は備品の閲覧・追加・変更権限を持つ。Django全体のユーザー管理やDB管理者の権限と区別し、全システムのsuperuserを通常利用のアプリ管理者として配布しない。

## 2. 利用者が行う操作

一般利用者は一覧を開く・再読み込みする。管理者はログイン、新規備品の登録、必要に応じた編集・公開状態の切替、ログアウトを行う。

| 操作 | 一般利用者（ログイン不要） | アプリ管理者（ログイン必須） |
| --- | --- | --- |
| 公開備品の閲覧 | 可 | 可 |
| 非公開備品の閲覧 | 不可 | 管理画面で可 |
| 備品の新規登録・編集 | 不可 | 可 |
| 公開／非公開の切替 | 不可 | 可 |

一般入口は「備品一覧・閲覧専用」、管理入口は「備品管理」と表示する。管理画面にはログイン中のユーザー名とログアウト操作を表示する。管理者がログイン済みでも一般入口は閲覧専用とする。授業では同じ学生が管理者役で登録し、一般利用者役で公開結果を確認するのであり、一般利用者へ登録権限を与える仕様ではない。

### 管理者ログインの確定仕様

- 方式: Django標準のユーザー名・パスワード認証とsessionを使用する。独自の認証コードは学生の課題にしない。
- 入口: 踏み台内browserから`http://admin.lab.test:8080/admin/`。未ログイン時はログイン画面を表示し、成功後に備品管理画面へ進む。
- アカウント: 各独立Labにアプリ管理者を1件作成する。基本ユーザー名は`lab_admin`。OSのuserやPostgreSQLのroleとは別のIDとする。P/Mで変更する値の詳細はD11で確定する。
- 作成: 教員が配布する補助commandを学生がWebサーバー上で実行する。補助commandは有効なstaffアカウントと備品の閲覧・追加・変更権限を設定し、superuserにはしない。一般画面に会員登録機能は設けない。
- パスワード: 学生がそのLab専用の12文字以上の値を対話入力し、確認のため2回入力する。全Lab共通の固定パスワードや実サービスのパスワードは使わない。教員提供commandで長さとDjango標準のパスワード検証を行い、Djangoの仕組みでハッシュ化して保存する。教材・採点結果へ実際の値を記録しない。
- ログイン失敗: ユーザー名とパスワードを確認する案内を表示し、管理操作を許可しない。アカウントの存在有無を個別に表示しない。
- ログアウト: Django標準のログアウト操作でsessionを無効化し、以後の管理操作には再ログインを要求する。授業終了時の操作手順に含める。
- パスワードを忘れた場合: Webサーバー内で対話式のパスワード変更commandを使う手順を教員が提供する。メールによる再設定、外部ログイン、多要素認証は今回の完成要件に含めない。
- D07の列単位DB権限に合わせ、上記は教員提供のpassword列だけを更新する補助commandとする。Django標準の全列更新command/formをそのまま使わず、browser内のpassword変更入口は提供しない。詳細はDB設計。
- 権限確認: 踏み台から接続できても、未ログインまたは必要な権限がない場合の登録・編集要求はサーバー側で拒否し、DBを変更しない。画面のボタン非表示だけでは完了としない。

必須実演の手順:

1. 学生PCで一般画面を開き、初期の公開備品を確認する。
2. 踏み台で管理者入口を開き、そのLab用のアカウントでログインする。
3. 指定された架空の備品を1件登録し、「公開する」を選んで保存する。
4. 一般画面を再読み込みし、同じコード・名前・数量・場所が表示されることを確認する。
5. DBサーバー内の読み取りSQLで、同じコードのrecordが保存されていることを確認する。

登録対象は架空の物品・架空の場所とし、大学の実台帳、学生個人情報、実アカウントの資格情報は使わない。

## 3. DBへ保存するデータ

完成構成のDB名は`jdu_catalog`、主たる業務tableは`catalog_item`とする。各fieldを定義したmodelとmigrationは教員が配布する。学生はmodelやmigrationをコーディングしない。

| field | 内容 | 制約 |
| --- | --- | --- |
| id | 自動採番の識別子 | 学生は入力しない |
| code | 備品コード | 必須、重複不可、最大32文字 |
| name | 備品名 | 必須、最大100文字 |
| quantity | 数量 | 必須、0以上の整数 |
| location | 架空の保管場所 | 必須、最大100文字 |
| description | 説明 | 任意、最大500文字 |
| is_public | 一般画面へ表示するか | 新規登録時の初期値は非公開 |
| created_at / updated_at | 作成／更新時刻 | 自動記録 |

初期データ例は公開状態の`DEMO-PC-001 / 練習用ノートPC / 3 / 練習室A`と`DEMO-KB-001 / 練習用キーボード / 5 / 練習棚B`。非公開サンプルも1件用意し、一般画面の表示条件を確認できるようにする。

Djangoの認証・権限・session・管理操作の記録に必要な補助tableも作成される。業務tableが一つであることを、DB全体にtableが一つしかないという意味にしない。

実行用DB roleは`catalog_app`。一覧取得・登録・編集・session処理等に必要なtable/列単位の権限だけを付与し、superuser・DB/role作成・DDL・備品DELETE権限を与えない。migrationと管理者初期作成は所有者`catalog_setup`で行い、終了時にNOLOGIN・password消去とする。[D07のDB設計](2026-10_web_infrastructure_database_design.md)の権限表と工程を正本にする。

備品、管理者の認証・権限、sessionはPostgreSQLを使用し、SQLiteへ自動fallbackしない。画面へアプリ用DB password、Django SECRET_KEY、管理者password等を表示しない。

## 4. 完成を確認する条件

| ID | 必須の確認 | 期待結果 |
| --- | --- | --- |
| APP-01 | 一般入口の表示 | 指定した公開備品がWebに表示され、非公開備品は出ない |
| APP-02 | 管理者入口の分離 | 踏み台から管理portへ到達し、ログイン後に登録できる |
| APP-03 | DB登録 | 新しく入力した備品コードのrecordがPostgreSQLに存在する |
| APP-04 | DB→Webの反映 | 一般画面でそのrecordの内容を取得して表示できる |
| APP-05 | 必要な接続設定 | Web内のアプリがdb.lab.testを解決し、DB用roleで5432へ接続する |
| APP-06 | 管理入口の非公開 | 公開HTTP80経由で/adminと配下を利用できず、許可されない送信元から8080へ到達できない |
| APP-07 | アプリの起動 | 指定serviceが起動し、Nginx→Gunicorn→Django→DBの経路で動く |
| APP-08 | 認証と操作権限 | 正しい管理者IDでログインできる。誤った認証、未ログイン、権限なしの登録・編集要求ではDBが変化しない。ログアウト後は再認証が必要 |

自動判定は、期待データ・現在の接続とservice・DBのrecord・公開／禁止経路を確認する。admin操作の自動試験に用いる認証、データの作成・後片付け等の詳細はD11で別途定義する。実際のbrowserでの管理者登録実演と、判定器の検証を分ける。

backup/restore、破壊的障害シナリオ、追加の貸出業務等を合格条件に加えない。これらのAPP条件は最終システムの必須動作。システム素点の最新案はD11 v0.2、科目25点への換算は教師が別に行う。

## 5. 学生の設定と教員の配布

### 教員が用意するもの

- Djangoプロジェクト、一般画面、管理画面設定、model/migration、入力検証、認証設定。
- 架空の初期データ、指定recordの確認に使う読み取りSQL、管理者作成用の補助command。
- 使用版を固定したアプリbundle、Python runtimeの必要資源、Django/Gunicorn/driverの依存一式とオフライン導入方法。
- `app.env`とNginx/systemdの編集用template、設定項目の説明、練習と課題の値。
- 初期化・migration・static資源配置の操作手順と補助command、設定異常時の確認案内。
- 自動判定の仕様と実装。正しいapp codeと設定作業を分けて配布する。

### 学生が必須で行うアプリ関連の設定

| 設定 | 学生が行うこと | 学習上の目的 |
| --- | --- | --- |
| DB接続 | `DB_HOST=db.lab.test`、`DB_PORT=5432`、DB名、実行用role、passwordを設定fileへ指定 | DNS・通信・DB認証の関係を確認 |
| 実行 | 配布templateに従いservice実行user、配置先、設定fileを指定して起動 | OSのuser・権限・serviceとアプリを接続 |
| Web転送 | Nginxの一般80・管理8080からloopbackのアプリへ転送し、static資源も配信 | Web serverとアプリの役割を分ける |
| 内部名 | admin.lab.testをWebのprivate IPへ対応させ、WebからDB名を解決 | 人の管理とアプリの名前解決を確認 |
| 管理者アカウント | 配布補助commandを実行し、Lab専用のpasswordを対話入力 | アプリ管理者とOS/DBのIDを区別 |
| 正常動作 | 管理画面で指定備品を登録し、公開画面とSQLで確認 | DBの書込みと読取りを一続きで確認 |

学生はPython、HTML、JavaScript、model、migration、認証処理を編集しない。設定fileの値変更、コマンド実行、Nginx/systemd設定、基本SQLを学習対象にする。サイト名の変更は任意の見た目調整とし、それだけを必須採点項目にしない。

`DEBUG=False`、SECRET_KEY生成、入力検証、CSRF対応等のアプリ側の基本制御は教員が用意する。ALLOWED_HOSTSは接続先の内部名と現在の公開IPv4を明示し、接続元IPの許可とは区別する。停止・起動で公開IPv4が変わる場合の更新方法を配布手順へ含める。秘密値はGit、画面、採点結果、通常のlogへ出力しない。

P/Mは同じ配布アプリと設定の種類を使い、DB名・role名・登録する備品等を変える方式にする。具体的なP/M対象分離とparameterはD11で確定し、P完了だけでMをPASSにしない。5台の固定IPを演習ごとに変更することは要求しない。

## 選定した実行構成

- Python 3、Django 5.2 LTS系、Gunicorn、PostgreSQL driverをWeb EC2へ配置する。調査時のDjango公式掲載は5.2.18。授業配布のpatch版・全依存・hashはD08の収録試験で固定する。
- Django/GunicornはWeb内の`127.0.0.1:8000`だけで待受する。
- Nginx一般入口はTCP80。管理入口はWebのprivate IPのTCP8080、到達元はSG-Bastionだけとする。
- admin.lab.testは10.20.1.20を返す内部A recordとする。追加EC2は作らない。
- 公開HTTP80の/adminと配下をNginx等で拒否する。リンクを隠すだけ、管理者ログインだけ、private IPでlistenするだけでは管理入口の分離を実現したと扱わない。SGとWeb側の経路制限を合わせて確認する。
- 必須の新規ネットワーク許可は「SG-Bastion→SG-Web TCP8080」。同一ホストのTCP8000をSGで外へ許可しない。
- 管理操作は踏み台内browserから実施する授業用HTTP。外部への一般HTTPの公開方針は維持し、管理認証情報を公開入口へ入力させない。実データや本番業務用のサービスへ転用する仕様ではない。
- 2026-10-13の最新ユーザー指示で、自己署名証明書・HTTPSの追加は撤回された。証明書作成・TLS設定は今回の必須課題に含めず、一般80・管理8080のHTTP構成を維持する。
